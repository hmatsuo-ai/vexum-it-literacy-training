# Theme 06｜ARIS・常駐業務

- 区分：POST-HIRE
- 想定受講段階：常駐前

## 1. このテーマの目的

ARIS・常駐業務の役割、顧客との関係、1日の基本行動に加え、**現場に入り込むことで業務を理解し、既存ツールの導入・システム開発・利用者教育・継続改善までつなげるVEXUMの現場伴走型支援**を理解する。

常駐を「顧客から指示された作業をこなす働き方」と捉えず、現場の課題や変化を捉えて改善へつなげる役割として理解させる。

## 2. 対象者・前提知識

Theme 01を理解している常駐予定者。入社前セミナーでは詳細を扱わない。

## 3. 到達目標

- ARIS／常駐人材の役割と提供価値を説明できる。
- 現場観察・ヒアリングから課題を発見し、改善候補へ整理する基本的な流れを説明できる。
- 独自システム開発だけでなく、既存SaaS・業務ツールの選定・紹介・導入・設定・連携も解決策になることを理解する。
- 「既存ツールで解決する部分」と「開発が必要な部分」を分けて考えられる。
- ITに不慣れな利用者へ、導入した仕組みの目的・操作方法・注意点を分かりやすく説明する必要性を理解する。
- 現場から得たフィードバックを短いサイクルで改善へ反映する考え方を説明できる。
- アジャイル開発とウォーターフォール開発の基本的な違いを説明し、案件に応じて使い分ける必要があることを理解する。
- 出勤から退勤までの基本的な業務フローを説明できる。
- 日報、進捗、課題、次アクションを事実ベースで報告できる。
- 顧客の指示とVEXUMのルールが不明確・矛盾する場合に相談できる。

## 4. 必須学習内容

### 4.1 ARIS・常駐人材の役割

- 顧客企業、VEXUM、本人の関係
- 顧客の現場で実際の業務を見る・聞く・理解すること
- いきなりシステム化せず、業務フロー、手作業、属人化、判断が必要な箇所を整理すること
- 課題の優先順位をつけ、小さく改善を始めること
- 顧客の意見をその場で確認し、次の改善へつなげること

### 4.2 解決手段は「開発」だけではない

課題に対して、最初から独自システム開発を前提にしない。

主な選択肢として以下を扱う。

- 既存SaaS・業務ツールをそのまま導入する
- 既存ツールの設定・運用方法を改善する
- 複数の既存ツールを連携する
- GAS・API・自動化ツール等で不足部分を補う
- 必要な部分を独自開発する
- 既存ツールと独自開発を組み合わせる

選択時は、機能適合、導入速度、費用、保守性、拡張性、セキュリティ、現場の使いやすさ等を確認する。

VEXUMは、既存ツールで十分に解決できる場合には、適切なツールの選定・紹介・導入・設定・運用支援まで行い、不要な独自開発を目的化しないことを伝える。

### 4.3 導入後の教育・定着支援

システムやツールは「導入したら完了」ではない。

- 何のために使う仕組みなのかを説明する
- ITに不慣れな利用者にも分かる言葉で操作を説明する
- 実際の画面を使って操作を見せる
- 現場でつまずいた箇所を確認する
- 必要に応じて手順・設定・画面・運用方法を改善する
- 特定の担当者しか使えない状態にせず、組織へ定着させる

「作れること」だけでなく、**顧客が使えること・使い続けられること**を成果として扱う。

### 4.4 アジャイルとウォーターフォール

| 観点 | アジャイル型 | ウォーターフォール型 |
| --- | --- | --- |
| 進め方 | 小さな単位で設計・実装・確認・改善を繰り返す | 要件定義・設計・実装・テスト等を工程ごとに順番に進める |
| 要件 | 利用結果や新しい発見をもとに調整しやすい | 初期に要件・仕様を明確にして計画通り進めることを重視 |
| フィードバック | 短い間隔で利用者の意見を反映しやすい | 工程やレビュー単位で確認するため、大きな変更は影響範囲が広くなりやすい |
| 向く案件 | 変化が多い、現場で試さないと最適解が分かりにくい案件 | 要件が比較的固定され、工程・承認・契約を厳密に管理する案件 |

アジャイルを「計画なしでその場で作る方法」、ウォーターフォールを「古くて悪い方法」と説明しない。

VEXUMの常駐型支援では、現場の利用者と近い距離で、

**観察 → 課題整理 → 小さく導入・開発 → 使ってもらう → 意見を聞く → 修正する**

というサイクルを回しやすいため、アジャイル型の改善と相性が良い。ただし、要件・契約・法令・セキュリティ等に応じてウォーターフォール型や両者を組み合わせた進め方も選択する。

### 4.5 常駐日の基本運用

- 1日の業務フロー
- 日報・進捗報告の基本
- ネクストアクションの考え方
- 顧客情報・資料・アカウントの扱い
- 困ったときの相談ルート
- 顧客側とVEXUM側の判断・報告先を混同しないこと

## 5. 扱わない内容

- 全クライアントに共通しない個別運用の一般化
- 顧客の正式ルールより教材を優先すること
- 既存ツールを調査せず独自開発を選ぶこと
- 「常駐しているから顧客の依頼をすべてその場で実装してよい」という考え方
- アジャイルを理由に要件、セキュリティ、権限、テスト、記録を省略すること
- アジャイルとウォーターフォールを単純な優劣で説明すること

## 6. 推奨学習構成

常駐の目的 → 現場観察 → 課題整理 → 解決手段の選択 → アジャイル／ウォーターフォール → 導入・開発 → 利用者教育 → フィードバック・改善 → 日報・報告 → 困ったとき → ケース演習

## 7. 実務ケース

顧客先で、担当者が毎日1時間かけてExcelへ売上データを転記している。

受講者に以下を考えさせる。

1. まず現場で何を確認するか
2. 既存の表計算・自動化・SaaS等で解決できないか
3. 独自開発が必要なのはどの部分か
4. 最初に小さく試すなら何を実装・導入するか
5. 利用者へどのように使い方を説明するか
6. 使ってもらった後、どの意見を次の改善へ反映するか

また、仕様が法律・契約等で厳密に固定された別ケースを提示し、アジャイル型とウォーターフォール型のどちらが適するかを理由付きで考えさせる。

## 8. 演習

### 演習1：現場改善

架空の業務フローから、作業を以下に分類する。

- 既存ツールで改善できる
- 設定・連携・自動化で改善できる
- 独自開発を検討する
- 人の判断を残す
- 追加ヒアリングが必要

その後、最初の1回で全部作るのではなく、最初に試す最小単位と、その結果を確認する方法を決める。

### 演習2：利用者への説明

ITに不慣れな顧客へ新しい仕組みを説明する想定で、

**目的 → 変わる作業 → 操作手順 → 注意点 → 困ったときの確認先**

の順に説明する。

### 演習3：日報・報告

架空の1日の業務記録から、日報を「実施内容／結果／課題／次アクション」に整理する。

## 9. 理解度確認

次を自分の言葉で説明できるか確認する。

1. 常駐することが、単に顧客先で作業することと何が違うか
2. なぜ既存ツールの導入と独自開発を両方検討するのか
3. なぜ導入後の操作説明・教育・定着支援が必要なのか
4. アジャイルとウォーターフォールの基本的な違い
5. VEXUMの常駐支援がアジャイル型の改善と相性が良い理由
6. どのタイミングで誰に何を報告・相談するか

## 12. 完成条件

- 最新の常駐運用と矛盾していない。
- 常駐人材が現場観察から課題整理・改善まで関わることが説明されている。
- 独自システム開発だけでなく、既存ツールの選定・紹介・導入・連携も解決手段として説明されている。
- ITに不慣れな顧客への操作説明・教育・定着支援が役割として説明されている。
- アジャイルとウォーターフォールの違いを優劣ではなく適性として説明している。
- VEXUMの常駐モデルが短いフィードバックサイクルを回しやすいことを説明している。
- 受講者が初日の基本業務と相談ルートを説明できる。
