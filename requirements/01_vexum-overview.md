# Theme 01｜VEXUMとは

- 区分：SEMINAR-CORE
- 想定受講段階：セミナー冒頭

## 1. このテーマの目的

受講者が「VEXUMは何をする会社か」だけでなく、**一般的なITコンサルの典型的な仕事との違いを理解し、VEXUMでは自分が企業の現場に入り、AIやテクノロジーを使って実際の業務を変えていく仕事に関われることを具体的にイメージできる状態**を作る。

Theme 01は単なる会社説明にしない。

受講者が終了時に、

> 「VEXUMで何をするのか分かった。自分も実際の企業課題をAIで解決できるようになりたい」

と思えることを重要な到達点とする。

## 2. 対象者・前提知識

面接後、契約・入社前のセミナー参加者。前提知識なし。

ITコンサル、DX、AI導入、常駐、アジャイル、ウォーターフォールといった言葉を知らない受講者でも理解できる表現を使う。

## 3. 到達目標

- VEXUMの事業・顧客・提供価値を自分の言葉で説明できる。
- AIを販売すること自体が目的ではなく、AIやテクノロジーを使って顧客業務を改善する会社であることを説明できる。
- VEXUMの常駐人材が現場に入り、業務理解から改善・定着まで継続的に関わる意味を説明できる。
- 課題に応じて、独自システムを開発するだけでなく、既存のSaaS・業務ツールの選定・紹介・導入・設定・運用支援も選択肢になることを説明できる。
- 導入したシステムやツールを、ITに不慣れな利用者にも使える形で説明・教育し、定着まで支援することがVEXUMの提供価値に含まれると理解する。
- アジャイル開発とウォーターフォール開発の基本的な違いを説明し、VEXUMの現場密着型支援がなぜアジャイル型の改善と相性が良いのかを説明できる。
- 一般的なITコンサルの典型的な関わり方と、VEXUMが重視する関わり方の違いを説明できる。
- VEXUMでは「提案して終わり」ではなく、現場理解、課題整理、実装、導入、教育、定着、改善まで関わることをイメージできる。
- 自分が研修後にどのような力を身につけ、顧客先で何をするのかをイメージできる。
- 次の研修へ進む意味を理解し、AI・業務改善をさらに学ぶ意欲を持てる。

## 4. 必須学習内容

### 4.1 VEXUMは何をする会社か

最低限、以下を扱う。

- VEXUMのMission・存在意義
- どのような企業課題を対象としているか
- AI、人、現場を組み合わせて業務改善を進めるという考え方
- 常駐人材が顧客の現場に入り、実際の業務を観察・ヒアリングしながら改善を進めること
- AIは目的ではなく、売上向上、コスト削減、業務効率化、データ活用などを実現するための手段であること
- 解決策は独自システム開発に限定せず、既存SaaS・業務ツールの選定、紹介、導入、設定、連携、自動化も含めて考えること
- 「作るか、既存ツールを使うか」は、機能適合、導入速度、費用、保守性、拡張性、現場の使いやすさ等を見て判断すること
- 導入した仕組みを現場で実際に使えるよう、操作説明・教育・運用サポート・定着支援まで行うこと
- 顧客の現場に近い位置で課題を理解し、現場の意見を短いサイクルで改善へ反映する考え方
- VEXUM Academy → 実務研修 → ARIS／顧客支援という人材育成の大まかな流れ

制度名や細かなプラン説明は最小限にし、「受講者自身がこの仕事にどうつながるか」を優先する。

### 4.2 一般的なITコンサルとVEXUMの違い

**Theme 01全体の30〜40％程度を、この比較の説明に割く。**

ここでいう「一般的なITコンサル」は業界全体を一括りに断定するものではなく、プロジェクト型ITコンサルの典型例として説明する。実装・常駐・運用改善まで行うITコンサル会社も存在するため、VEXUMの違いは「できる／できない」ではなく、**どこに重心を置いた事業モデルか**として説明する。

| 観点 | 一般的なITコンサルの典型 | VEXUMが重視する形 |
| --- | --- | --- |
| 顧客との距離 | 外部の専門家としてプロジェクト単位で支援 | 常駐人材が顧客の現場に近い位置へ入り、継続的に支援 |
| スタート地点 | ある程度定義された経営課題・IT課題・システム案件 | 日々の業務の「面倒」「属人化」「手作業」など、まだ整理されていない課題も対象 |
| 主な仕事 | 調査、戦略、要件定義、システム選定、導入支援など | ヒアリング、現場観察、課題整理、既存ツール導入、システム開発、業務自動化、教育、運用定着、改善までつなげる |
| 解決手段 | プロジェクト目的に応じて製品選定や開発を行う | 「自社で作る」ことを目的にせず、既存ツールと独自開発を組み合わせて最適な手段を選ぶ |
| 成果物の考え方 | 提案書、要件定義書、システム導入等がプロジェクト成果になることが多い | 実際に現場で使われ、業務が変わり、成果が出る状態までを重視 |
| AIの位置づけ | 数あるITソリューションの1つとして扱う場合も多い | AIを業務全体に組み込み、企業のAI活用レベルを継続的に高めていくことを重視 |
| 関わる期間 | プロジェクトの開始・終了が明確なケースが多い | 現場で試し、使ってもらい、改善するサイクルを継続することを重視 |
| 利用者支援 | プロジェクトにより研修・定着支援を行う | ITに不慣れな利用者への操作説明や教育を含め、現場で使い続けられる状態を重視 |
| 人材の役割 | 特定領域のコンサルタント・エンジニアとして参画 | 現場理解とAI・ITの両方を使い、顧客と一緒に改善を進める人材を育成 |
| 成功の見方 | プロジェクト完遂、要件達成、導入完了など | 売上・コスト・時間・業務品質など、顧客の実際の変化につながったかを重視 |

#### 受講者に最も伝えたい違い

VEXUMで働く人は、単に「AIについて詳しい人」になることが目的ではない。

顧客の現場で、

**聞く → 観察する → 課題を整理する → 解決手段を選ぶ → 導入・開発する → 使い方を伝える → 実際に使ってもらう → 結果を見る → 改善する**

という一連の流れに関わる。

つまり、受講者が今後身につけるべき力は、AIツールの知識だけではなく、

- 顧客の困りごとを理解する力
- 課題を構造化する力
- 既存ツールと独自開発を比較して解決手段を選ぶ力
- AIやITを使って解決策を作る力
- ITに不慣れな人にも分かるように説明する力
- 実際の現場で使える形まで落とし込む力
- 結果を見て改善する力

であることを伝える。

### 4.3 「提案して終わり」ではなく「現場が変わるまで」

抽象的な会社紹介だけではなく、業務改善の一連の流れを具体例で見せる。

例：

> 毎月、多数の書類を社員が目視で確認している。

この場合、いきなり「AIシステムを作りましょう」と考えない。

1. 何を確認しているのか聞く
2. 現在の業務フローを見る
3. どこに時間がかかっているか整理する
4. データや既存ツールを確認する
5. 既存SaaS・AI・GAS・独自開発等から適した手段を選ぶ
6. 既存ツールで十分なら導入・設定・連携を支援し、不足する部分だけ開発する
7. 小さく現場で試す
8. ITに不慣れな利用者にも操作方法と目的を説明する
9. 本当に時間が減ったか、ミスが減ったか確認する
10. 現場の意見を聞いて改善する

この流れそのものがVEXUMの仕事の面白さとして伝わる構成にする。

### 4.4 アジャイル開発とウォーターフォール開発

VEXUMの現場密着型支援を理解するため、開発方式の違いを初学者向けに扱う。

| 観点 | アジャイル型 | ウォーターフォール型 |
| --- | --- | --- |
| 基本の進め方 | 小さな単位で「確認 → 設計 → 実装 → テスト → フィードバック」を繰り返す | 要件定義 → 設計 → 実装 → テスト → リリースのように工程を順番に進める |
| 要件の扱い | 実際に使った結果や新しい発見を反映しながら調整しやすい | 初期に要件・仕様を明確にし、その計画に沿って進めることを重視 |
| リリース・確認 | 小さく早く試し、短い間隔で確認しやすい | 大きな工程単位で成果を確認する形になりやすい |
| 向いている状況 | ニーズが変化する、現場で使わないと最適解が分かりにくい、早く試したい | 要件が比較的固定されている、工程・承認・契約を明確に管理する必要がある |
| 変更への対応 | 各サイクルで優先順位や仕様を見直しやすい | 後工程での大きな変更は影響範囲が広くなりやすい |

重要なのは、**アジャイルが常に優れていて、ウォーターフォールが古いという説明にしないこと**である。案件の規模、要件の確実性、契約、セキュリティ、法令、承認プロセス等によって適切な進め方は異なる。

VEXUMの常駐・現場伴走型支援は、担当者が現場で利用者の反応や業務上の変化をすぐ確認できるため、

**現場を見る → 小さく試す → 使ってもらう → 意見を聞く → 修正する**

というアジャイル型の改善サイクルと特に相性が良いことを説明する。ただし、すべての案件をアジャイルで進めると断定しない。

### 4.5 VEXUMで働く・学ぶ面白さ

会社紹介の最後には、受講者自身へ接続する。

- 学んだAIをすぐ実際の企業課題へ使える
- 業界の異なる企業の業務を知ることができる
- 顧客の「困っている」が、自分の作った仕組みや導入したツールで変わる経験ができる
- 開発だけでなく、既存ツールの選定・導入・連携・教育・定着も経験できる
- AIだけでなく、業務理解・要件定義・開発・データ活用・顧客教育など幅広い力が身につく
- 最初からすべてできる必要はなく、研修・NEXUS・OJTを通して段階的に身につける

「会社のルールを覚えさせる時間」ではなく、**これから何を学べるのかを楽しみにさせる時間**として設計する。

## 5. 扱わない内容

- 「ITコンサルは資料を作るだけ」など、他社・他業界を不当に単純化する説明
- 「VEXUMだけが現場支援をしている」など事実として確認できない差別化表現
- 他社を下げることでVEXUMを良く見せる構成
- 「アジャイルなら要件定義や計画が不要」「ウォーターフォールは使うべきでない」といった誤った二項対立
- 既存ツールより独自開発を常に優先する考え方
- 根拠が更新されていない売上・導入社数・成長率
- 組織図、役職、料金プランなど細かな制度説明
- Mission・Vision・Valuesの文言暗記
- 採用広告のような抽象的な「成長できます」「未来を変えます」だけの説明

## 6. 推奨学習構成

1. **企業にはどんな困りごとがあるか**
   - 手作業、属人化、情報が散らばっている、AIを使いたいが何から始めればよいか分からない等
2. **ITコンサルとはどんな仕事か**
   - 初学者向けに典型的な役割を説明
3. **ではVEXUMは何が違うのか**
   - 比較表と具体例を使い、Theme 01で最も時間をかける
4. **VEXUMならどう解決するか**
   - 顧客課題 → 現場観察・ヒアリング → 既存ツール／開発の選択 → 導入・実装 → 教育 → 定着 → 改善
5. **なぜ現場密着型は改善が速いのか**
   - アジャイルとウォーターフォールの違い → 現場フィードバックを短いサイクルで反映する価値
6. **自分はそこで何をするのか**
   - 研修 → NEXUS → OJT・顧客支援への接続
7. **ミニケース演習**
   - 実際の業務課題をVEXUMならどう考えるか体験する

## 7. 実務ケース

架空の企業を設定する。

> 社内にExcelや紙の資料が散らばっており、問い合わせ対応も毎回ベテラン社員が行っている。経営者から「AIを導入したい」と相談された。現場にはITに不慣れな利用者も多い。

受講者にいきなりツールを選ばせるのではなく、

- まず何を聞くか
- 何が本当の課題か
- どの業務から改善すべきか
- 既存ツールで解決できるか、新しいシステムを作る必要があるか
- 小さく試すなら何から始めるか
- 利用者へどのように使い方を伝えるか
- 現場の意見を次の改善へどう反映するか
- どうなれば成功と言えるか

を考えさせる。

「AIを導入する会社」や「システムを作る会社」だけではなく、**企業の課題を理解し、既存ツールと開発を含む必要な方法を選び、導入・教育・改善までつなげる会社**という認識を作る。

## 8. 演習

### ミニワーク：あなたがVEXUMの担当者なら？

顧客の困りごとを1つ提示し、以下を3〜5分で考える。

1. 最初に顧客へ聞きたいこと
2. 現場で確認したいこと
3. 既存ツールで解決する部分と、開発が必要そうな部分
4. 最初に小さく試す内容
5. 利用者への説明・教育で必要なこと
6. 効果をどう確認し、次の改善へつなげるか

正解を当てることより、**課題を聞かずにツールや開発へ飛びつかない思考**を体験させる。

## 9. 理解度確認

暗記問題ではなく、次の3点を確認する。

### 確認1

「一般的なITコンサルの典型とVEXUMの違いは？」という質問に対し、1分程度で説明できる。

### 確認2

具体的な顧客課題を1つ提示し、

- 何を確認するか
- 既存ツールと独自開発をどう比較するか
- VEXUMが導入・教育・改善までどのように関われそうか
- 何を成果として確認するか

を説明できる。

### 確認3

アジャイルとウォーターフォールの違いを説明し、VEXUMの現場伴走型支援がアジャイル型の改善と相性が良い理由を説明できる。ただし、案件によってウォーターフォール型が適する場合もあることを理解している。
